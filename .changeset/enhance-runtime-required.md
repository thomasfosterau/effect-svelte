`Forms.enhance` (in `./client`) now requires its `{ runtime }` option, typed to provide every service the handlers require, whenever `onSubmit`, `onResult` or `onError` requires a service. Before, such a call type-checked without a runtime and the handler died with a missing-service defect when it ran; it is now a type error. This is a type-only change: calls whose handlers require no services keep the options optional, calls that already pass a runtime providing those services are unchanged, and the code it rejects is code that dies with a missing-service defect once a handler reaches the service it requires (or that passes an options object whose type leaves `runtime` optional). `onSubmit` and `onResult` (and `runtime`) are now declared `?: … | undefined`, so a handler or runtime forwarded as `undefined` (for example by spreading `{ onResult: undefined }`) type-checks under `exactOptionalPropertyTypes`. Each handler's requirements are inferred separately, so handlers that require different services (say `onSubmit` one service and `onResult` or `onError` another) type-check with a runtime that provides all of them, and a runtime missing any of them is still rejected. A missing runtime is reported on the `Forms.enhance` call, and a runtime that lacks a service on the runtime, never on a handler (even when an `onError` passed by name requires a service and another handler's parameters are not annotated). A function that wraps `Forms.enhance` for a generic `R` forwards its options as `...options: EnhanceOptionsArgs<R>` (newly exported from `./client`), or takes a required `{ runtime: EnhanceRuntime<R> }`; forwarding an `EnhanceOptions<R>`, whose `runtime` is optional, no longer type-checks. An effect typed as requiring `any` or `unknown` is treated as requiring no services, so no runtime is demanded: such a type names no service a runtime could be checked against, so a handler (or `onError`) annotated, say, `Effect.Effect<void, never, any>` still type-checks without a runtime.
